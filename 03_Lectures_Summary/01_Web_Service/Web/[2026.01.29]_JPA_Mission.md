# JPA Mission (Jan 29 - Jan 30)

## 1. step01

* 객체 지향적 연관관계 및 참조 불가 문제

    * Member1과 Team1 엔티티가 물리적인 테이블 구조에만 의존하고 있어, 객체 레벨에서의 연관관계 매핑 (Join)이 이루어지지 않았습니다. 이로 인해 객체 그래프 탐색 (예: `member.getTeam()`)을 통한 상호 참조가 불가능한 구조적 결함이 있습니다.

* 식별자 (Sequence) 생성 전략의 공유 문제

    * 별도의 시퀀스 전략이 설정되지 않아 하이버네이트 기본 시퀀스 (hibernate_sequence)를 공용으로 사용합니다. 결과적으로 두 테이블의 ID 값이 각각 관리되지 않고, 실행 순서에 따라 번호가 통합되어 부여되는 문제가 발생합니다.

* 데이터 정합성 및 외래 키 참조 불일치

    * Member1의 teamId를 단순히 숫자값으로 직접 입력하고 있어, Team1의 실제 생성된 PK 값과 일치하지 않거나 존재하지 않는 팀 ID가 저장될 수 있는 데이터 정합성 문제가 존재합니다.

* 원시 타입에 대한 `@NonNull` 어노테이션의 무효성

    * Member1의 teamId 필드는 원시 타입인 `long`으로 선언되어 있습니다. 원시 타입은 기본적으로 null을 허용하지 않으므로, Lombok의 `@NonNull` 어노테이션은 실질적인 역할을 수행하지 못합니다. 이를 해결하려면 래퍼 클래스인 `Long`을 사용하거나 해당 어노테이션을 제거해야 합니다.

## 2. step02

* 여전히 해소되지 않은 객체 간 연관관계 매핑 문제

    * step01과 동일하게 Member2와 Team2 사이의 물리적/객체적 연관관계 매핑 (Join)이 구현되지 않았습니다. 여전히 Member2는 팀의 객체가 아닌 단순 숫자값만을 보유하고 있습니다.

* 테이블별 독립적 시퀀스 적용 및 성능 최적화

    * 각 엔티티에 `@SequenceGenerator`를 개별적으로 설정하여, 테이블마다 독립적인 시퀀스 전략을 갖도록 개선되었습니다.

    * `allocationSize = 50` 설정을 통해 DB 시퀀스 호출 횟수를 줄이고 메모리에서 번호를 할당하는 성능 최적화가 반영되었습니다.

* 시퀀스 할당 간격(Gap)에 따른 식별자 불연속성

    * 시퀀스 할당 사이즈가 50으로 설정되어 있어, 애플리케이션이 재실행될 때마다 DB 시퀀스는 다음 범위 (예: 1 → 51 → 101)로 건너뛰게 됩니다.

    * 이로 인해 사용되지 않은 번호들이 버려지면서 식별자 값의 연속성이 보장되지 않고 큰 공백이 생기는 특성이 있습니다. 이는 성능을 위한 의도된 설계이나, 번호의 순차적 결합이 중요한 비즈니스 로직에서는 주의가 필요합니다.

## 3. step03

* 객체 참조 기반의 일대일 (`@OneToOne`) 단방향 연관관계 형성

    * Member3가 단순 숫자값이 아닌 Team3 객체를 직접 참조하게 됨으로써, 객체 그래프 탐색이 가능한 진정한 의미의 연관관계 매핑이 이루어졌습니다.

    * `@JoinColumn`을 통해 `team_id`라는 외래 키 (FK)가 생성되었으며, 이를 통해 테이블 간의 물리적 Join이 형성됩니다.

* 도메인 제약 조건에 따른 예외 발생 (teamName null 불허)

    * Team3의 `teamName` 필드에는` @NonNull`과 `nullable = false` 설정이 되어 있습니다.

    * 따라서 `new Team3()`와 같이 이름을 생략하고 생성된 빈 객체를 영속화하려 할 경우, 데이터베이스의 `NOT NULL` 제약 조건 위배로 인해 예외가 발생합니다.

* 영속 상태 (Persistence Context) 관리 및 외래 키 참조 오류

    * `em.persist(new Member3("박지성2", new Team3("Fisa")))`와 같이 실행할 경우, 참조되는 Team3 객체는 아직 데이터베이스에 저장되지 않은 비영속 (Transient) 상태입니다.

    * JPA는 외래 키 값을 저장할 때 참조하는 대상의 PK 값이 존재해야 하지만, Team3가 영속화되지 않아 ID값이 없으므로 정상적인 외래 키 참조가 불가능하여 에러가 발생합니다.

## 4. step04

### 4.1 step01

* **DDL (`CREATE`, `DROP`, `ALTER`):** 실행 즉시 데이터베이스에 물리적으로 반영되는 자동 커밋 특성을 가지므로, 트랜잭션의 롤백 범위에서 제외됩니다.

* **DML (`INSERT`, `UPDATE`, `DELETE`):** 데이터의 상태를 변경하는 작업으로 트랜잭션 (tx) 내에서 관리되며, `commit()` 전까지는 실제 DB에 반영되지 않아 롤백이 가능합니다.

### 4.2 step02

```Java
List<Member4> all = team.getMembers();
System.out.println(all); //순환참조
```

* Lombok `@ToString`에 의한 무한 루프 및 StackOverflowError 발생

    * Member4와 Team4 두 엔티티 모두에 Lombok의 `@ToString `어노테이션이 사용되었습니다.

    * `team.getMembers()`를 통해 리스트를 출력하면 Team4의 `toString()`이 실행되고, 그 과정에서 리스트 내부의 Member4 객체들의 `toString()`을 호출합니다.

    * 다시 Member4의 `toString()`은 필드에 있는 Team4 객체의 `toString()`을 호출하게 되어, 두 객체가 서로를 무한히 호출하다가 StackOverflowError가 발생하며 프로그램이 비정상 종료됩니다.

* 양방향 참조 시의 `toString` 편의성 문제

    * 이는 JPA 자체의 문제라기보다는, 객체의 모든 필드를 자동으로 문자열화하는 Lombok의 편의 기능이 양방향 참조 구조와 충돌하여 발생하는 현상입니다.

### 4.3 step03

Member 엔티티 조회 시 연관된 Team 정보를 언제, 어떻게 가져오는지 비교

#### 1. `@ManyToOne` / `@ManyToOne(fetch = FetchType.EAGER`

* 동작: Member를 조회하는 순간, JPA가 자동으로 조인(JOIN) 쿼리를 생성하여 Team 정보까지 한꺼번에 메모리에 올립니다.

* 단점:

    * 리소스 낭비: 화면에서 Member 정보만 필요할 때도 무조건 Team 객체를 생성하므로 불필요한 메모리가 소모됩니다.

    * 성능 저하: 연관된 엔티티가 많아질수록 복잡한 조인 쿼리가 발생하며, 이는 실무에서 N+1 문제의 주원인이 됩니다.

#### 2. `@ManyToOne(fetch = FetchType.LAZY)`

* 동작: Member 조회 시 Team은 실제 DB에서 가져오지 않고 가짜 객체인 프록시를 채워둡니다. 이후 member.getTeam().getName()처럼 실제 데이터에 접근하는 시점에만 추가 SQL을 실행합니다.

* 장점:

    * 최소 쿼리 실행: 필요한 시점에만 조회를 수행하므로 초기 조회 속도가 매우 빠르고 불필요한 조인을 방지합니다.

    * 유연성: 특정 비즈니스 로직에서만 Team 정보가 필요한 경우 매우 효율적입니다.
